# NagarSeva

NagarSeva is a local-first municipal complaint registration and tracking platform. The current implementation includes the Phase 0 foundation, Phase 1 authentication/dashboard shell, Phase 2 citizen directory, Phase 3 complaint registration and tracking, the Phase 4 text-based AI session engine, Phase 5 local voice input and output, Phase 6 complaint photo attachments, Phase 7 simulation campaigns and reports, and Phase 8 stabilization (tests, security review, accessibility, monitoring, backups, staging deployment).

## Structure

```text
frontend/       React + TypeScript + Vite admin application
backend/        Express + TypeScript API, Sequelize migrations and seeders
```

Exotel and WhatsApp are not configured.

## Prerequisites

- Node.js 20 LTS or newer and npm
- A local MySQL 8 server (for example, managed through phpMyAdmin)
- An ElevenLabs API key with Speech-to-Text and Text-to-Speech permissions for voice sessions

## Run locally

1. Configure `backend/.env` using `backend/.env.example` as a reference.
2. Create the configured database in MySQL/phpMyAdmin and make sure the MySQL server is running.
3. Install dependencies with `npm install`.
4. Apply schema migrations with `npm run db:migrate`.
5. Add the demo organization with `npm run db:seed`.
6. Run `npm run db:seed:admin` to create the local development administrator.
7. Start frontend and backend with `npm run dev`.
8. Optional, for voice sessions: set `ELEVENLABS_API_KEY` in `backend/.env`.

The Vite frontend is at <http://localhost:5173>. The API health endpoint is <http://localhost:5000/api/v1/health>; it reports API and MySQL status. Manage the local MySQL service and database through your installed MySQL/phpMyAdmin setup.

## Configuration

The backend validates required settings at startup with Zod. Set local values in `backend/.env`; keep real credentials out of version control. `CORS_ORIGIN` accepts a comma-separated allow-list. The database health check is intentionally a readiness check and returns HTTP 503 if MySQL cannot be reached.

Authentication uses revocable database-backed sessions in HttpOnly cookies. The bootstrap administrator seeder is for local development only and refuses to run when `NODE_ENV=production`. Citizen records are organization-scoped, normalize Indian mobile numbers, and keep documented contact authorization separate from opt-out. CSV/XLSX imports preview column mappings and row outcomes before writing. API endpoints are described in `backend/openapi.yaml`.

Complaint intake records staff-entered reports only after an explicit confirmation attestation. Ticket IDs are generated by the API; assignment, status history, and internal notes are organization-scoped and permission-checked. After pulling schema changes, run `npm run db:migrate` and `npm run db:seed` from the repository root before using the complaint screens.

## AI sessions (Phase 4, text mode)

The **AI call studio** (`/studio`) runs a simulated complaint conversation with typed citizen replies. A deterministic, rule-based dialogue engine (`backend/src/ai/`) follows the blueprint state machine: AI disclosure, language choice (Assamese, Hindi, English), problem, location and landmark, name (skipped when the citizen record already has one), read-back, and a yes/no confirmation. The citizen can say "stop" at any point, choose a detail to correct after a "no", and is handed off after repeated unclear answers.

The engine never creates complaints. The backend registers a complaint only after an explicit "yes" to the read-back, through the same guarded `createComplaint` path used by staff, in one transaction with the session update. Each session can create at most one complaint, enforced by the service, an idempotency key, and a unique index. Sessions, their messages, and the questionnaire version they used are stored in `call_sessions`, `session_messages`, and `questionnaire_versions`. **Sessions** (`/sessions`) shows outcomes and transcripts.

Permissions: `sessions:run` (Super Admin, Municipal Admin) and `sessions:read` (those roles plus Auditor). Sessions cannot be started for inactive or opted-out citizens. Assamese and Hindi wording in `backend/src/ai/questionnaireContent.ts` needs review by fluent speakers before any real-citizen use.

## Voice sessions (Phase 5)

When ElevenLabs is configured, the call studio offers **Voice (microphone)** input. The browser asks for microphone permission only when a voice session starts, and releases the microphone when the session ends or you leave the page. Recording stops automatically after a pause, after 8 seconds with no speech, or after 30 seconds. The assistant's replies are spoken, and listening can resume automatically. Typing is always available as a fallback.

The backend sends the recording directly to ElevenLabs and keeps nothing: no audio is written to disk or the database. A transcription is used only if it passes all of these checks:

- its confidence is at least `STT_MIN_CONFIDENCE` (default 0.4);
- it is in the script of the expected language;
- it does not look like a recogniser hallucination (repetition loops or broken characters).

Otherwise the assistant asks the citizen to repeat, and the transcript records that the speech was not understood. Confidence is saved on each spoken citizen message. Recognition is never biased towards expected answers, because testing showed a "yes/no" hint could turn "yes" into "no".

Microphone access needs `localhost` or HTTPS. Opening the dev server through a LAN IP over HTTP blocks the microphone. Validate Assamese, Hindi, and English recognition with native speakers before real-citizen use.

## Complaint photos (Phase 6)

The complaint page has a **Photos** section. Staff who can work on the complaint (Super Admin, Municipal Admin, or the assigned Operator) can upload photos. Auditors can view them. Staff can also create a **citizen upload link**: a URL that works without an account, expires after `UPLOAD_LINK_TTL_HOURS` (default 48), accepts up to `UPLOAD_LINK_MAX_UPLOADS` photos (default 5), and can be revoked. A complaint can have at most 3 active links. The link is shown once, and only a SHA-256 hash of its token is stored. In simulation, links are not sent to anyone; copy and share them manually for testing.

Upload rules:

- Only JPG, PNG and WebP photos up to `MAX_UPLOAD_SIZE_MB` (default 10) are accepted.
- A file is accepted only if its declared type, its extension and its actual contents (file signature) agree, so renamed files are rejected.
- Files are saved under `UPLOAD_DIR` (default `backend/storage/uploads`, gitignored) with random names; the uploaded file name is kept for display only.
- MySQL stores only metadata: uploader, source, size, type and SHA-256 checksum.

Photos are served only through an authenticated, permission-checked endpoint that never allows them to run as a page. Each view is recorded in the audit log. The public upload endpoints are rate limited. Photo metadata such as GPS location (EXIF) is currently kept as uploaded.

## Simulation campaigns (Phase 7)

**Campaigns** (Super Admin and Municipal Admin) plan a controlled batch of test conversations. Nothing is dialled and no messages are sent.

1. **Create a draft.** Give it a name and a target group (wards, locality text, preferred language), a conversation language, text or voice input, and 1–3 attempts per citizen.
2. **Preview eligibility.** This builds the recipient list. A citizen is included only if their record is active, has a valid Indian mobile number, has documented consent (authorization flag, consent source and consent date), has not opted out, and is not already waiting in another live campaign. Everyone else is listed with the reason they were excluded. A campaign can include at most 100 eligible recipients.
3. **Start simulation, then Run next recipient.** This opens the next citizen's conversation in the AI call studio. When it ends, the studio offers **Run next recipient** so staff can work through the queue. Eligibility is checked again for each recipient, so anyone who opts out after the preview is skipped.
4. **Pause, resume or cancel.** Pause blocks new conversations. Cancel skips everyone still waiting and ends any open test session. The campaign completes automatically once nobody is waiting.

A conversation that reached the citizen counts as completed, whatever they chose (including "stop"); it is never repeated. A hand-off counts as failed. Extra attempts are used only when staff abort a test session, and only while the campaign is live.

## Reports (Phase 7)

**Reports** (`reports:read`) shows key figures and charts for a date range (last 7, 30 or 90 days, or custom):

- complaints over time, and by status, category and ward;
- AI session outcomes and languages;
- campaign completion.

Every figure is aggregated on the server, and dates are grouped by `REPORT_UTC_OFFSET` (default `+05:30`). Users without `complaints:read_all` only see complaints assigned to them, in the charts and in the CSV export alike. The complaint CSV export contains no citizen names or phone numbers, neutralises spreadsheet formulas, and is recorded in the audit log. Each chart has a **Table** view with the same numbers. The dashboard now also shows finished sessions, complaints awaiting review, and live campaigns.

## Stabilization (Phase 8)

- **Tests:** `npm test` runs the backend unit tests, the API integration suite and the browser suite. The integration suite covers the blueprint's 14-step acceptance scenario, organization isolation, role permissions, CSRF and idempotency. The browser suite covers the acceptance scenario in Chrome, WCAG 2.1 AA scans of every page, and phone-width layout. Both run on a throwaway `nagar_seva_test` database. Details are in [docs/OPERATIONS.md](docs/OPERATIONS.md#5-tests).
- **Monitoring:** JSON logs with a request ID on every response, and the error reference shown to users. Health checks are at `/api/v1/health` (readiness) and `/api/v1/health/live`.
- **Backups:** `scripts/backup.sh`, `scripts/verify-backup.sh` (tested restore) and `scripts/restore.sh`.
- **Staging:** `docker-compose.staging.yml` (MySQL, API and HTTPS web front via Caddy), configured from `deploy/staging.env`.
- **Security:** findings and accepted risks are in [docs/SECURITY_REVIEW.md](docs/SECURITY_REVIEW.md). In production the API refuses to start with development defaults.
- **Demo:** [docs/DEMO_SCRIPT.md](docs/DEMO_SCRIPT.md).
